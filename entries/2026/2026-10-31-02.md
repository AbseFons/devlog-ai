## Objetivo
Aprender a utilizar ramas protegidas y pull requests para integrar código de forma segura, evitando cambios directos en la rama principal y asegurando la calidad mediante revisiones antes del despliegue.

## Explicación
En entornos profesionales, nunca se debe hacer commit directo en la rama principal (main o master). La estrategia estándar es crear una rama de funcionalidad desde el desarrollo, implementar los cambios y luego abrir un pull request. Este mecanismo obliga a que otro desarrollador revise el código antes de fusionarlo. Git Flow formaliza esto con ramas específicas para releases y hotfixes. Al configurar protección en la rama principal en plataformas como GitHub o GitLab, se activan reglas que bloquean merges sin revisión aprobada. Esto reduce errores en producción y mantiene un historial claro del trabajo colaborativo.

## Ejemplo (no ejecutado automáticamente)
Creación de una rama de funcionalidad y simulación de un pull request con mensaje de commit descriptivo.

```bash
git checkout -b feature/nueva-autenticacion
git add . && git commit -m 'feat: implementar login con OAuth2'
```

## Ejercicio
Crea una rama llamada issue/123-corrección-bug, haz un commit de prueba y simula el envío de un pull request a la rama main.

## Criterios de revisión
Debe existir la rama creada correctamente, tener al menos un commit con mensaje que incluya 'fix' o 'bug', y no haber hecho cambios directos en la rama main.
