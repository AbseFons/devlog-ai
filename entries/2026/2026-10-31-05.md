## Objetivo
Distinguir claramente el rol de la autenticación (quién eres) de la autorización (qué puedes hacer) al diseñar endpoints seguros, evitando errores comunes de seguridad.

## Explicación
En las arquitecturas de API modernas, la autenticación y la autorización son pasos secuenciales pero distintos. La autenticación verifica la identidad del usuario mediante credenciales como tokens JWT o OAuth2, respondiendo a '¿Quién eres?'. Una vez validada esta identidad, el sistema de autorización evalúa los permisos asociados a ese sujeto contra las políticas de acceso, respondiendo a '¿Qué puedes hacer?'. Un error frecuente es confiar únicamente en la autenticación para conceder acceso a recursos sensibles. Por ejemplo, un usuario autenticado no debe tener acceso automático a todos los datos; cada recurso debe verificar explícitamente si el sujeto posee el rol o permiso necesario (como 'admin' o 'editor'). Implementar ambos mecanismos de forma separada y jerárquica es fundamental para prevenir fugas de información y violaciones de seguridad.

## Ejemplo (no ejecutado automáticamente)
Endpoint que verifica primero el token de autenticación y luego consulta la base de datos de roles para decidir si permite la lectura del recurso solicitado.

```javascript
const user = await verifyToken(req.headers.authorization);
if (!user) return res.status(401).json({ error: 'No autenticado' });
const permissions = await db.query('SELECT roles FROM users WHERE id = ?', [user.id]);
if (!permissions.includes('read_data')) return res.status(403).json({ error: 'Sin permisos' });
return res.json({ data: req.body.resource });
```

## Ejercicio
Crea un endpoint que reciba un token en el header y una ruta de recurso. Implementa lógica para denegar acceso si el usuario no existe (401) o si el usuario existe pero carece del rol 'analista' para ese recurso específico (403).

## Criterios de revisión
El código debe separar la validación del token de la consulta de permisos. Debe devolver códigos HTTP distintos para falta de autenticación y falta de autorización. No debe exponer detalles internos de la base de datos en los mensajes de error.
