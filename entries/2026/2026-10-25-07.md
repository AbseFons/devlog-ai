## Objetivo
Aprender a implementar estrategias de versionado en APIs REST para garantizar la compatibilidad hacia atrás y facilitar la evolución del servicio sin romper clientes existentes.

## Explicación
El versionado es crítico para mantener la estabilidad de las APIs. Existen dos enfoques principales: versionado por URL (ej. /v1/users) y versionado por encabezados (ej. Accept: application/vnd.api+json;version=2). El primero es explícito pero ensucia la ruta; el segundo es más limpio pero menos visible para cachés intermedios. En esta lección, utilizaremos la estrategia de URL con un parámetro opcional en el endpoint de usuarios. Esto permite que los clientes antiguos sigan usando /users mientras los nuevos acceden a /v2/users. La respuesta del servidor debe incluir cabeceras como 'Deprecation' y 'Link' para guiar la migración gradual, asegurando una transición suave entre versiones.

## Ejemplo (no ejecutado automáticamente)
Definición de rutas en un archivo de configuración de API que soporta dos versiones simultáneas con diferentes esquemas de respuesta.

```bash
route /users GET "application/json;version=1" "[{\"id\": 1, \"name\": \"Ana\"}]"
route /v2/users GET "application/vnd.api+json" "[{\"data\": {\"id\": 1, \"attributes\": {\"name\": \"Ana\"}}}]"
```

## Ejercicio
Crea un endpoint POST /v1/items que acepte JSON plano y otro en /v2/items que acepte JSON anidado con metadatos.

## Criterios de revisión
El código debe diferenciar claramente las estructuras de datos entre versiones y devolver códigos HTTP distintos si el cliente no especifica la versión correcta.
