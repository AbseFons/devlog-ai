## Objetivo
Comprender que una clase debe tener un solo motivo para cambiar, evitando la complejidad innecesaria y manteniendo el código modular y fácil de probar en arquitecturas modernas.

## Explicación
El principio de Responsabilidad Única establece que cada clase debe encargar exactamente una tarea. Cuando mezclamos lógica de negocio con persistencia o notificaciones, complicamos las pruebas y aumentamos el riesgo de errores. Imagina un servicio de usuario: si maneja tanto la validación de datos como el envío de correos electrónicos, cualquier cambio en la política de correos afectará a la clase entera. Separar estas responsabilidades permite que cada módulo evolucione independientemente. Esto facilita la implementación de patrones como Dependency Injection y mejora significativamente la mantenibilidad del sistema a largo plazo.

## Ejemplo (no ejecutado automáticamente)
Clase separada para enviar correos electrónicos, desacoplada de la lógica principal del usuario.

```javascript
class EmailService {
  async send(userEmail, message) {
    console.log(`Enviando correo a ${userEmail}: ${message}`);
  }
}
```

## Ejercicio
Refactoriza una clase 'Usuario' que actualmente valida datos y guarda en base de datos. Extrae la lógica de persistencia a una nueva clase 'RepositorioUsuario'.

## Criterios de revisión
El código debe mostrar dos clases distintas, sin dependencias directas entre ellas, y el método principal debe inyectar o usar el repositorio como dependencia.
