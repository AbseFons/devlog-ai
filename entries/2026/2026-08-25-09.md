## Objetivo
El desarrollador distinguirá cuándo usar un stub para proporcionar datos simulados versus un mock para validar interacciones, aplicando cada uno en pruebas de integración sin depender de servicios externos reales.

## Explicación
En la arquitectura de pruebas, los stubs y mocks cumplen funciones distintas. Un stub es una implementación simplificada que devuelve valores predefinidos inmediatamente para evitar dependencias externas lentas o costosas, permitiendo que el sistema bajo prueba avance sin esperar respuestas de red. Por otro lado, un mock no solo simula datos, sino que registra las llamadas realizadas al objeto simulado. Esto permite validar si se invocarón métodos específicos con los argumentos correctos. La confusión común surge al intentar verificar interacciones usando un stub; para ello es necesario usar mocks que incluyan verificaciones de estado tras la ejecución del código.

## Ejemplo (no ejecutado automáticamente)
```python
from unittest.mock import Mock, patch

def procesar_pago(tipo_transaccion):
    if tipo_transaccion == 'credito':
        return {'estado': 'aprobado', 'monto': 100}
    return {'estado': 'rechazado'}

# Stub: Simula la respuesta de una pasarela sin conexión real
pasarela_mock = Mock()
pasarela_mock.procesar.return_value = {'estado': 'pendiente'}

resultado = procesar_pago('credito')
assert resultado['estado'] == 'aprobado'

# Mock con verificación de interacción
with patch('mi_modulo.pasarela_real') as mock_pasarela:
    mock_pasarela.procesar.return_value = {'estado': 'pendiente'}
    procesar_pago('debito')
    # Verifica que el método fue llamado una vez
    assert mock_pasarela.procesar.call_count == 1
```

## Ejercicio
Crea un script que defina una función `enviar_notificacion` que llame a un servicio externo. Implementa un stub para simular la respuesta exitosa del servicio y luego modifica el código para usar un mock que verifique que el método `enviar` fue invocado exactamente dos veces con diferentes parámetros.

## Criterios de revisión
El script debe importar correctamente las clases Mock y Stub, definir la función de negocio original, sustituir la dependencia externa por un stub en la primera prueba, y usar un mock con assertions para validar el número de llamadas y los argumentos pasados en la segunda prueba.
