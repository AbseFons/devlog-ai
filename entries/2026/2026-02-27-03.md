## Objetivo
Comprender que una clase debe tener un solo motivo para cambiar, evitando la complejidad innecesaria y mejorando el mantenimiento del código mediante la separación de responsabilidades claras.

## Explicación
El principio de Responsabilidad Única establece que cada clase o módulo debe encargar exactamente una tarea. Cuando mezclamos lógica de negocio con persistencia de datos en un mismo archivo, cualquier cambio en la base de datos obliga a modificar el código de negocio, aumentando el riesgo de errores. Al separar estas responsabilidades, creamos componentes modulares y reutilizables. Por ejemplo, si necesitamos cambiar cómo se guarda un usuario, solo debemos tocar la capa de persistencia sin afectar la lógica que calcula su bonificación. Esto facilita las pruebas unitarias y permite escalar el sistema más fácilmente.

## Ejemplo (no ejecutado automáticamente)
Clase separada para calcular bonificaciones versus clase para guardar datos en base de datos, demostrando cómo evitar acoplamiento innecesario.

```javascript
class CalculadoraBonificacion {
  calcular(sueldo) { return sueldo * 0.1; }
}
class RepositorioUsuario {
  guardar(usuario) { console.log('Guardado en DB'); }
```

## Ejercicio
Refactoriza una clase 'Empleado' que actualmente calcula su salario y guarda sus datos en un archivo JSON, dividiéndola en dos clases distintas.

## Criterios de revisión
El código debe tener al menos dos clases separadas, ninguna clase debe realizar operaciones de E/S mientras calcula lógica de negocio, y los tests deben pasar independientemente para cada módulo.
