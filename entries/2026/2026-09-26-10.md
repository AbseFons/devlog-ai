## Objetivo
Aprender a utilizar códigos HTTP específicos para errores, mejorando la legibilidad y permitiendo que los clientes manejen excepciones de forma precisa sin depender únicamente de mensajes de texto genéricos.

## Explicación
El diseño robusto de errores en una API va más allá del código 400 o 500. Es crucial distinguir entre un error de validación (422 Unprocessable Entity), que indica datos incorrectos pero no necesariamente inexistentes, y un error de autenticación fallida (401 Unauthorized) tras el agotamiento de intentos (429 Too Many Requests). Al estructurar las respuestas JSON con campos 'error' y 'message', facilitamos la depuración. Por ejemplo, devolver 409 Conflict es vital cuando un recurso ya existe, diferenciándolo de un error de lógica interna del servidor (500). Esta precisión permite a los desarrolladores frontend mostrar mensajes de usuario contextualizados, como 'El correo ya está registrado' en lugar de un genérico 'Error al guardar'.

## Ejemplo (no ejecutado automáticamente)
Respuesta JSON para un error de conflicto por duplicidad de recurso con código 409.

```javascript
const response = {
  status: 409,
  error: "Conflict",
  message: "El correo electrónico ya está registrado en el sistema."
```

## Ejercicio
Crea una función que simule la creación de un usuario y devuelva un objeto JSON con estado 409 si el email existe, o 201 si es nuevo.

## Criterios de revisión
El código debe incluir lógica condicional para verificar la existencia del usuario antes de responder. La respuesta de error debe contener exactamente los campos 'status', 'error' y 'message'. El mensaje debe ser claro en español.
