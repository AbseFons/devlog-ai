## Objetivo
Establecer una convención clara para organizar el código fuente en un repositorio, separando lógica de negocio, configuración y pruebas para mejorar la mantenibilidad del proyecto desde su inicio.

## Explicación
Un diseño de repositorio sólido comienza con una estructura de carpetas predefinida que refleja la arquitectura del software. Para aplicaciones monolíticas, se recomienda ubicar las entidades de dominio en 'src/domain', la lógica de aplicación en 'src/application' y los controladores en 'src/controllers'. La configuración específica del entorno debe residir en un directorio separado como 'config'. Las pruebas unitarias van a 'tests/unit' y las de integración a 'tests/integration'. Esta separación física facilita la navegación, el onboarding de nuevos desarrolladores y la ejecución paralela de diferentes tipos de pruebas sin conflictos. Mantener esta disciplina evita la acumulación de código disperso que dificulta la refactorización futura.

## Ejemplo (no ejecutado automáticamente)
Estructura de directorios para una aplicación web básica con separación clara entre capas.

```bash
# Estructura base del repositorio
mkdir -p src/domain src/application src/controllers config tests/unit tests/integration
# Crear archivo de configuración inicial
touch config/database.yml
```

## Ejercicio
Crea un nuevo repositorio llamado 'mi-proyecto' y genera la estructura de directorios descrita en el ejemplo. Luego, añade un archivo README.md en la raíz explicando brevemente qué hace cada carpeta.

## Criterios de revisión
El repositorio debe contener exactamente los 9 directorios especificados (src/domain, src/application, src/controllers, config, tests/unit, tests/integration y el root). El archivo README.md debe existir en la raíz y describir al menos tres de las carpetas principales.
