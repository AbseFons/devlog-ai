## Objetivo
Distinguir conceptualmente entre merge y rebase en Git, entendiendo cómo cada uno afecta la historia del proyecto y cuándo aplicar cada estrategia para mantener un historial limpio o preservar ramas paralelas.

## Explicación
Git ofrece dos métodos principales para integrar cambios: merge y rebase. Merge crea un nuevo commit de fusión que preserva la topología original, mostrando claramente las divergencias temporales entre ramas. Es ideal para flujos de trabajo colaborativos donde se desea mantener el historial exacto de cuándo se fusionaron líneas de desarrollo. Por otro lado, rebase mueve los commits de una rama sobre la punta de otra, creando una línea de tiempo lineal y cronológica. Esto resulta en un historial más limpio pero no refleja fielmente el orden real de las operaciones. Elige merge para estabilidad y transparencia; elige rebase para limpieza visual antes de fusionar a main.

## Ejemplo (no ejecutado automáticamente)
Comandos básicos para realizar un merge y luego un rebase en una rama local, mostrando la diferencia visual en el historial.

```bash
git checkout feature
# Realiza cambios y commit
git checkout main
git merge feature
git log --oneline --graph
# Para limpiar el historial:
git rebase main
```

## Ejercicio
Crea dos ramas llamadas 'dev' y 'fix'. Haz un commit en cada una. Fusiona 'fix' a 'dev' usando merge, luego intenta rebase sobre la rama principal.

## Criterios de revisión
El historial debe mostrar primero el nodo de fusión tras el merge, y luego una línea recta sin nodos intermedios tras el rebase exitoso.
