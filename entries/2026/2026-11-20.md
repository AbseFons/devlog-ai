## Objetivo
Aprender a invertir las dependencias para que las clases de alto nivel no dependan de implementaciones concretas, sino de interfaces, facilitando pruebas unitarias y flexibilidad en el diseño del sistema.

## Explicación
El principio L de SOLID establece que la dependencia debe dirigirse hacia abstracciones. En lugar de que una clase concrete dependa directamente de otra implementación concreta, ambas deben depender de una interfaz o tipo genérico. Esto desacopla los módulos, permitiendo intercambiar implementaciones sin alterar el código del cliente. Por ejemplo, si tienes un servicio de notificaciones, no debes programar para 'EmailSender' específicamente, sino para 'INotificationService'. Así, puedes cambiar la implementación a 'SMSNotifier' o 'PushNotifier' simplemente inyectando una nueva instancia, manteniendo la lógica de negocio intacta y promoviendo un código más modular y mantenible.

## Ejemplo (no ejecutado automáticamente)
Clase cliente que depende de una interfaz INotificationService en lugar de una implementación concreta, permitiendo inyección de dependencias.

```javascript
interface INotificationService {
  send(message: string): Promise<void>;
}

class EmailNotifier implements INotificationService {
  async send(msg: string) { console.log('Email:', msg); }
}

async function processOrder(orderId: number, service: INotificationService) {
  await service.send(`Order ${orderId} confirmed`);
}
```

## Ejercicio
Crea una interfaz 'IDatabase' con un método 'save'. Implementa dos clases concretas: 'SqlDatabase' y 'MockDatabase'. Modifica una función existente para que reciba 'IDatabase' como parámetro en lugar de una clase concreta.

## Criterios de revisión
El código debe compilar sin errores, la función principal debe aceptar cualquier implementación de la interfaz IDatabase, y no debe haber referencias directas a las clases concretas dentro de la lógica del cliente.
