## Objetivo
Comprender las técnicas principales para gestionar versiones en APIs, asegurando la compatibilidad hacia atrás y planificando la obsolescencia de endpoints antiguos sin interrumpir servicios existentes.

## Explicación
El versionado es crucial para mantener la estabilidad de los clientes mientras evolucionan los servidores. Existen tres enfoques comunes: versionado por URL (ej. /v1/users), por encabezados HTTP (ej. Accept: application/vnd.api+json;version=2) y parámetros de consulta (?version=1). La estrategia por URL es la más explícita y fácil de depurar, ideal para APIs públicas. El uso de encabezados permite mantener rutas limpias pero puede ser menos visible en logs básicos. Los parámetros son simples pero pueden ensuciar las URLs. Se recomienda comenzar con versionado por URL para mayor claridad. Debe definirse una política clara de ciclo de vida: soporte, mantenimiento y retirada. Nunca se deben eliminar endpoints sin previo aviso y un periodo de transición adecuado.

## Ejemplo (no ejecutado automáticamente)
Definición de rutas versionadas en un archivo de configuración de servidor web para exponer dos versiones distintas del recurso 'usuarios'.

```bash
location /api/v1/users {
    proxy_pass http://backend-v1;
}

location /api/v2/users {
    proxy_pass http://backend-v2;
}
```

## Ejercicio
Crea un archivo de configuración para tu servidor web que defina tres versiones de una API: v1, v2 y v3. Asigna cada versión a un backend diferente simulando la evolución del servicio.

## Criterios de revisión
El archivo debe tener bloques claros para cada versión con nombres distintos (v1, v2, v3). Cada bloque debe indicar claramente el backend al que se reenvía la solicitud. No deben existir rutas duplicadas ni errores de sintaxis.
