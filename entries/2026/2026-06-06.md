## Objetivo
Aprender a utilizar ramas protegidas y flujos de trabajo colaborativos en Git para evitar la corrupción del código principal, asegurando que cada contribución sea revisada antes de fusionarse al repositorio compartido.

## Explicación
En entornos profesionales, el flujo de desarrollo centralizado protege el estado estable del proyecto. La estrategia recomendada implica crear una rama de trabajo desde 'main' o 'develop', realizar los cambios locales y solicitar una Pull Request (PR) o Merge Request (MR). Esta solicitud activa revisiones por pares obligatorias antes de la fusión automática. Git no permite fusionar directamente en ramas protegidas sin aprobación, lo que previene errores humanos. Este proceso garantiza trazabilidad, calidad del código y estabilidad continua, fundamentales para cualquier equipo de ingeniería de software moderno.

## Ejemplo (no ejecutado automáticamente)
Crear una rama de característica, realizar cambios y preparar una solicitud de fusión hacia la rama principal.

```bash
git checkout -b feature/nueva-funcionalidad
git add . && git commit -m "Añadir nueva funcionalidad"
git push origin feature/nueva-funcionalidad
```

## Ejercicio
Crea una rama llamada 'fix/bug-critico', realiza un cambio en un archivo de configuración y envía los cambios a la rama remota.

## Criterios de revisión
El usuario debe haber creado la rama correctamente, realizado el commit con mensaje descriptivo y enviado los cambios al repositorio remoto sin errores.
