## Objetivo
Aprender a utilizar códigos HTTP apropiados para comunicar estados de error específicos, mejorando la legibilidad y facilitando el manejo de excepciones por parte del cliente.

## Explicación
El diseño robusto de errores en una API no se limita a devolver un mensaje genérico. Cada estado debe reflejar la naturaleza exacta del fallo. Utilizar códigos como 400 para peticiones malformadas, 401 para falta de autenticación o 404 para recursos inexistentes permite que los clientes implementen lógica específica. Por ejemplo, ante un 409 Conflict, el cliente puede intentar una operación idempotente con parámetros actualizados. Esta semántica clara reduce la carga de depuración y evita que las aplicaciones colapsen por errores inesperados.

## Ejemplo (no ejecutado automáticamente)
Respuesta JSON estándar para un error de validación (400 Bad Request) indicando el campo fallido.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "El correo electrónico proporcionado no es válido.",
    "details": [
      { "field": "email", "reason": "Formato incorrecto" }
    ]
  }
}
```

## Ejercicio
Crea una respuesta JSON para un error 500 Internal Server Error que incluya un código interno único y un mensaje genérico para no filtrar detalles sensibles.

## Criterios de revisión
La respuesta debe tener el código HTTP 500, un objeto 'error' con campos 'code', 'message' y 'details'. El mensaje debe ser seguro (sin stack traces) y el código interno debe ser una cadena alfanumérica.
