## Objetivo
Diferenciar conceptualmente y técnicamente el uso de merge y rebase para integrar ramas, entendiendo cómo cada comando afecta la historia del proyecto y cuándo aplicar uno u otro para mantener un historial limpio o preservar relaciones lógicas.

## Explicación
Merge crea un nuevo commit que fusiona dos líneas de desarrollo, preservando exactamente la topología original de las ramas. Esto resulta en una historia lineal con divergencias visibles. Rebase, por el contrario, toma los commits de la rama actual y los 'mueve' uno a uno sobre la punta de la rama base, creando nuevos commits con hashes distintos. Esto produce una línea de tiempo lineal y limpia, ideal para flujos de trabajo colaborativos donde se desea ocultar la complejidad de las fusiones intermedias. La elección depende de si priorizas la fidelidad histórica (merge) o la legibilidad futura (rebase).

## Ejemplo (no ejecutado automáticamente)
Comando rebase para mover los commits locales sobre el último commit remoto antes de push.

```bash
git fetch origin
git rebase origin/main
```

## Ejercicio
Crea una rama local 'feature-x', haz dos commits, luego ejecuta un merge con la rama principal. Borra los cambios y vuelve a hacer los mismos commits usando rebase sobre la rama principal.

## Criterios de revisión
El historial debe mostrar una línea recta sin nodos de fusión extraños tras el rebase, mientras que el merge debe mostrar claramente un nodo de unión entre las ramas.
