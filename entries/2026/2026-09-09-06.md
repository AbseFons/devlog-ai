## Objetivo
Aprender a integrar cambios mediante Pull Requests, definiendo criterios claros de revisión para mantener la calidad del código en reposos colaborativos sin bloquear el flujo de trabajo.

## Explicación
La integración continua se beneficia enormemente de los Pull Requests (PR). En lugar de fusionar directamente al rama principal, los desarrolladores abren un PR desde una rama de característica. Esto permite que otros revisen el código antes de la fusión. La estrategia clave es establecer reglas claras: ¿qué debe revisarse? ¿Se requieren pruebas automatizadas aprobadas? ¿Quién son los revisores obligatorios? Un buen flujo incluye descripciones detalladas del cambio, enlaces a tickets de gestión y comentarios constructivos. Esto reduce deuda técnica y evita que errores sutiles lleguen a producción. La revisión no es solo técnica, sino también de arquitectura y legibilidad.

## Ejemplo (no ejecutado automáticamente)
Crear un Pull Request con descripción clara y requisitos de aprobación definidos en el sistema de gestión del proyecto.

```bash
# Crear rama de feature
feature-branch checkout -b feature-login-page
# Realizar cambios y añadir archivos nuevos
echo 'Nueva funcionalidad de inicio de sesión' >> README.md
# Añadir archivo de prueba para la nueva funcionalidad
cat > test_login.js << 'EOF'
function testLogin() {
  console.log('Prueba de inicio de sesión exitosa');
}
testLogin();
EOF
# Subir cambios y crear Pull Request
git add .
git commit -m 'Añadir funcionalidad de login con pruebas'
git push origin feature-login-page
```

## Ejercicio
Abre un PR desde una rama local hacia main. Incluye al menos dos revisores y define tres criterios de aceptación en la descripción del PR.

## Criterios de revisión
1. Descripción clara del cambio con enlaces a tickets.
2. Al menos dos pruebas automatizadas aprobadas antes de la fusión.
3. Dos revisores técnicos deben aprobar el PR.
