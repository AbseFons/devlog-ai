## Objetivo
Comprender que una clase debe tener un solo motivo para cambiar, evitando la complejidad innecesaria y facilitando el mantenimiento del código en arquitecturas modernas.

## Explicación
El principio de Responsabilidad Única establece que cada clase debe encargar exactamente una razón para cambiar. En la práctica, esto significa evitar clases 'híbridas' que mezclan lógica de negocio con persistencia o presentación. Por ejemplo, si una clase maneja tanto el cálculo de impuestos como la conexión a la base de datos, cualquier cambio en la normativa fiscal obligará a modificar esa clase y podría romper la conexión a la base de datos. Separar estas responsabilidades permite que el módulo de impuestos evolucione independientemente del repositorio de datos. Este enfoque reduce los efectos secundarios no deseados, mejora la legibilidad y hace que las pruebas unitarias sean más directas y confiables.

## Ejemplo (no ejecutado automáticamente)
Clase separada para calcular impuestos versus clase híbrida que lo hace junto con la persistencia de datos.

```javascript
class CalculadoraImpuestos {
  calcular(tipo, monto) {
    return tipo === 'iva' ? monto * 0.21 : monto;
  }
}

class RepositorioVentas {
  guardar(venta) {
    // Lógica de persistencia
  }
}
```

## Ejercicio
Refactoriza una clase existente que maneje tanto la validación de formularios como el envío de correos electrónicos en dos clases distintas.

## Criterios de revisión
El código debe mostrar dos clases separadas, cada una con un único método público relevante y sin dependencias mutuas innecesarias.
