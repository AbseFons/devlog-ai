## Objetivo
Aprender a almacenar credenciales sensibles fuera del código fuente utilizando variables de entorno para evitar exponer claves en repositorios públicos y garantizar la seguridad básica de la aplicación.

## Explicación
Los secretos, como contraseñas o tokens API, nunca deben hardcodearse. La práctica estándar es inyectarlos mediante variables de entorno antes de iniciar el proceso. Esto permite que el mismo código funcione en desarrollo, pruebas y producción sin modificar su fuente. Herramientas como Docker o gestores de configuración leen estas variables automáticamente. Es crucial configurar el sistema operativo o el contenedor para que no muestre estos valores en los logs por defecto. Además, se recomienda usar herramientas especializadas como HashiCorp Vault o AWS Secrets Manager para rotación y acceso auditado, aunque las variables de entorno son el primer paso fundamental para cualquier desarrollador consciente de la seguridad.

## Ejemplo (no ejecutado automáticamente)
Script que define una variable de entorno segura y la utiliza en un script de inicialización simulado.

```bash
# Definir secreto en entorno (NO hardcodear)
export MI_TOKEN_SECRETO="sk_live_abc123xyz"
# Usar el secreto en la aplicación
echo "Conectando con token: ${MI_TOKEN_SECRETO}" > /tmp/app.log
```

## Ejercicio
Crea un archivo .env local con una variable llamada DB_PASSWORD y actualiza tu script de inicio para leerla sin exponerla en el historial del terminal.

## Criterios de revisión
El código debe usar variables de entorno, no strings literales para secretos; el archivo .env debe estar excluido del control de versiones (.gitignore); la aplicación no debe imprimir el valor completo del secreto en stdout.
