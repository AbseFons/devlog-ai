## Objetivo
Aprender a utilizar códigos HTTP específicos para errores, mejorando la legibilidad y permitiendo que los clientes manejen excepciones de forma precisa sin depender de mensajes genéricos.

## Explicación
El diseño robusto de una API requiere mapear cada tipo de fallo a un código HTTP adecuado. No basta con devolver un 500 para todos los errores internos; distinguir entre 'no encontrado' (404), 'malformado' (400) o 'conflicto' (409) permite al cliente frontend construir flujos de error específicos. Por ejemplo, intentar crear un usuario duplicado debe retornar 409 Conflict, no 500. Esto evita que las aplicaciones muestren mensajes genéricos como 'Error desconocido'. Al estructurar la respuesta JSON con el campo 'error' y detalles específicos, facilitamos la depuración. Un buen diseño anticipa estos estados antes de que ocurran, documentando claramente qué código esperar en cada escenario negativo.

## Ejemplo (no ejecutado automáticamente)
Respuesta JSON para un intento fallido de crear un usuario con email duplicado

```json
{
  "error": {
    "code": "DUPLICATE_EMAIL",
    "message": "El correo electrónico ya está registrado en el sistema."
  }
}
```

## Ejercicio
Crea un endpoint POST /users que valide la unicidad del email. Si existe, responde con código 409 y el objeto JSON de ejemplo. Si falta algún campo requerido, responde con 400.

## Criterios de revisión
El endpoint debe devolver exactamente el código HTTP 409 para emails duplicados y 400 para campos faltantes. La respuesta debe incluir un objeto 'error' con los campos 'code' y 'message'. No se deben usar códigos genéricos como 500 para estos casos.
