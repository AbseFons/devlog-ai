## Objetivo
Comprender cómo el aislamiento evita que una transacción lea datos modificados por otra no confirmada, garantizando la consistencia en sistemas concurrentes.

## Explicación
El nivel de aislamiento 'Read Committed' es fundamental para evitar lecturas sucias. Esto ocurre cuando una sesión lee un dato que ha sido actualizado por otra sesión pero aún no ha confirmado la transacción. En SQL Server, MySQL o PostgreSQL, esto se configura mediante el nivel de aislamiento por defecto. Si dos usuarios editan el mismo registro simultáneamente sin este control, podrían ver versiones intermedias corruptas. La base de datos utiliza bloqueos (locks) o snapshots para asegurar que cada lectura vea solo datos confirmados previamente. Esto es crucial en aplicaciones bancarias donde un retiro no debe verse reflejado inmediatamente por otra consulta hasta que la operación se complete y confirme.

## Ejemplo (no ejecutado automáticamente)
Script SQL que simula dos transacciones concurrentes para demostrar cómo el nivel de aislamiento 'Read Committed' evita ver datos no confirmados en una segunda lectura inmediata.

```sql
BEGIN TRANSACTION;
UPDATE cuentas SET saldo = saldo - 100 WHERE id = 1;
COMMIT;

BEGIN TRANSACTION;
SELECT saldo FROM cuentas WHERE id = 1;
-- Esta consulta verá el nuevo valor solo después del COMMIT anterior.
```
