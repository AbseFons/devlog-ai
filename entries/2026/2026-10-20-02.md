## Objetivo
Aprender a clasificar errores mediante códigos HTTP estándar para mejorar la legibilidad, facilitar el manejo automático de fallos por parte del cliente y mantener una arquitectura RESTful coherente y predecible.

## Explicación
El diseño robusto de una API comienza definiendo claramente qué significa cada error. No basta con devolver un mensaje genérico; es crucial utilizar los códigos de estado HTTP apropiados para categorizar la naturaleza del fallo. Un código 400 Bad Request indica que el cliente envió datos malformados, mientras que un 401 Unauthorized señala falta de credenciales válidas. Por otro lado, un 500 Internal Server Error comunica problemas internos del servidor sin exponer detalles sensibles. Esta distinción permite a los clientes construir flujos de recuperación específicos: reintentar tras un 503 o corregir el payload ante un 400. La consistencia en estos códigos reduce la carga cognitiva del desarrollador y mejora la experiencia del usuario final al proporcionar feedback preciso sobre por qué una operación falló.

## Ejemplo (no ejecutado automáticamente)
Respuesta JSON de una API que rechaza un cuerpo de solicitud inválido con el código 400 Bad Request, incluyendo un mensaje claro y un campo 'errors' detallado.

```json
{
  "statusCode": 400,
  "message": "Solicitud incorrecta",
  "errors": {
    "email": ["El formato del correo electrónico es inválido"]
  }
}
```

## Ejercicio
Crea una interfaz de usuario simple que simule el envío de un formulario. Implementa lógica para interceptar respuestas con código 400 y mostrar al usuario exactamente qué campo contiene errores, en lugar de un mensaje genérico de 'Error'.

## Criterios de revisión
La solución debe diferenciar visualmente entre errores de cliente (4xx) y del servidor (5xx). El manejo de errores 400 debe ser específico, mostrando el nombre del campo fallido. No se deben mostrar detalles internos del servidor al usuario final.
