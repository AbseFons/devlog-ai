## Objetivo
Diferenciar claramente entre autenticación (quién eres) y autorización (qué puedes hacer). Comprender que la primera valida identidad mediante tokens o credenciales, mientras la segunda aplica políticas de acceso basadas en roles o permisos específicos para proteger recursos.

## Explicación
En el desarrollo de APIs, es vital distinguir dos conceptos fundamentales. La autenticación responde a '¿Quién eres?' y verifica la identidad del usuario, típicamente mediante tokens JWT o sesiones. Por otro lado, la autorización responde a '¿Qué puedes hacer?' y determina los permisos específicos del usuario sobre recursos protegidos. Un error común es confundir ambos; un sistema puede saber quién es el usuario (autenticado) pero denegar el acceso a una ruta específica si no tiene los privilegios adecuados (no autorizado). Implementar ambos mecanismos de forma independiente asegura que, incluso si un token se filtra, el daño sea limitado por las restricciones de autorización.

## Ejemplo (no ejecutado automáticamente)
Un endpoint protegido que verifica primero el token de autenticación y luego comprueba los roles para autorizar la acción de eliminar un recurso.

```javascript
const user = req.user; // Objeto con 'roles' extraído del token
if (!user || !user.roles.includes('admin')) {
  return res.status(403).json({ error: 'No autorizado' });
}
// Lógica de eliminación segura
```

## Ejercicio
Crea un endpoint en tu API que requiera autenticación para listar usuarios, pero solo permita a los roles 'admin' y 'superuser' eliminar usuarios. Documenta qué responde la API ante un token válido sin permisos.

## Criterios de revisión
El código debe separar la lógica de validación del token de la lógica de verificación de roles. La respuesta de error para falta de autorización debe ser explícita (código 403). No se deben exponer detalles internos del sistema en los mensajes de error.
