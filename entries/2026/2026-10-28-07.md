## Objetivo
Aprender a diseñar esquemas de partición de datos en repositorios distribuidos para optimizar el rendimiento y la escalabilidad, evitando cuellos de botella en sistemas de alta concurrencia.

## Explicación
En arquitecturas de microservicios o bases de datos distribuidas, la partición es fundamental para escalar horizontalmente. Existen dos enfoques principales: partición por hash, que distribuye los datos aleatoriamente pero dificulta las consultas transversales, y partición por rango, que agrupa datos lógicamente cercanos, facilitando consultas locales a expensas de un desequilibrio potencial en la carga. La elección depende del patrón de acceso: si las consultas son globales, el hash es preferible; si son locales o temporales, el rango gana. Un diseño robusto considera también la reubicación dinámica de datos (resharding) para mantener el equilibrio ante cambios en el volumen de datos.

## Ejemplo (no ejecutado automáticamente)
Implementación de particionamiento por rango en una base de datos SQL usando sintaxis estándar para dividir una tabla de transacciones por fecha.

```sql
CREATE TABLE transactions (
  id INT PRIMARY KEY,
  amount DECIMAL(10,2),
  created_at TIMESTAMP
);

-- Crear particion por rango mensual
CREATE TABLE transactions_2026_oct (LIKE transactions) PARTITION BY RANGE (YEAR(created_at)) (
  PARTITION p2026_oct VALUES LESS THAN ('2027-01-01')
);
```

## Ejercicio
Diseña un esquema de partición para una tabla de logs de acceso web que guarde registros por IP. Explica cómo distribuirías los datos si las consultas son mayoritariamente por rango de fecha versus por IP.

## Criterios de revisión
El diseño debe especificar claramente el criterio de partición (hash, rango o lista), justificar la elección basada en los patrones de consulta y describir una estrategia para reequilibrar los datos si se detecta un desbalance significativo.
