## Objetivo
Diferenciar claramente cuándo utilizar merge para preservar la historia colaborativa versus rebase para crear una línea de desarrollo lineal y limpia antes de fusionar.

## Explicación
Merge crea un nuevo commit de fusión que mantiene el historial completo, incluyendo las ramas originales, ideal para trabajo en equipo donde la trazabilidad es crítica. Rebase reescribe el historial moviendo los commits de una rama a otra, resultando en una línea recta. Úsalo solo en ramas locales antes de subir, nunca en código compartido con otros, ya que esto puede causar conflictos de sincronización graves.

## Ejemplo (no ejecutado automáticamente)
Comandos para realizar un rebase local sobre la rama principal y luego hacer merge, mostrando la diferencia visual en el historial.

```bash
git checkout feature
# Realizar cambios locales
git add .
git commit -m "Añadir nueva funcionalidad"
git rebase main
# Verificar línea recta
git log --oneline --graph
```

## Ejercicio
Crea una rama 'feature' desde 'main', haz dos commits, vuelve a 'main', haz un commit y luego usa 'git rebase feature' para mover tus cambios encima del nuevo commit de main.

## Criterios de revisión
El historial debe mostrar los commits de la rama feature sobre el último commit de main sin crear un nodo de fusión intermedio. No deben existir conflictos no resueltos en el proceso de rebase local.
