## Objetivo
Aprender las tres estrategias principales para versionar una API (URL, Header y Query) y evaluar cuándo aplicar cada una según la complejidad del recurso y los requisitos de compatibilidad con clientes legacy.

## Explicación
El versionado es crucial para evolucionar sin romper clientes existentes. Existen tres enfoques: 1) Versionado por URL (ej. /v1/users), que es explícito pero ensucia la ruta. 2) Versionado por Header (ej. Accept: application/vnd.api+json;version=1), que mantiene las rutas limpias pero requiere soporte del cliente. 3) Versionado por Query (ej. ?version=1), fácil de implementar pero menos semántico. La elección depende de si el cambio es menor o mayor, y de la capacidad de negociación del cliente.

## Ejemplo (no ejecutado automáticamente)
Definición de rutas para una API de gestión de usuarios que soporta dos versiones distintas: una base (v1) con campos simples y otra avanzada (v2) con metadatos adicionales.

```javascript
const routes = {
  v1: '/api/v1/users',
  v2: '/api/v2/users'
};

// Rutas soportadas por el servidor
export default routes;
```

## Ejercicio
Crea un archivo 'routes.js' que exporte un objeto con las rutas para tres versiones de una API de pagos. Luego, escribe una función 'getVersionPath(version)' que devuelva la ruta correcta basada en una cadena de entrada.

## Criterios de revisión
El código debe manejar versiones válidas ('v1', 'v2', 'v3') y devolver null o un mensaje de error claro para versiones inexistentes. Asegúrate de que las rutas sigan el patrón '/api/{version}/payments'. Comenta cada ruta indicando qué campos nuevos introduce esa versión.
