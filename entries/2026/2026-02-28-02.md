## Objetivo
Distinguir conceptualmente entre merge y rebase en Git, entendiendo cómo cada uno afecta la línea de tiempo del historial de commits y cuándo es preferible usar uno u otro para mantener un código limpio.

## Explicación
Merge crea un nuevo nodo en el grafo de commits, preservando la historia lineal original y añadiendo una rama de fusión. Es seguro pero puede resultar en un historial ramificado y complejo. Rebase, por el contrario, reescribe la línea de tiempo moviendo los commits de una rama para que parezcan haber ocurrido después del merge. Esto produce un historial lineal y limpio, ideal para ramas de desarrollo personales, aunque debe evitarse en ramas compartidas públicas para no perder la historia real.

## Ejemplo (no ejecutado automáticamente)
Comandos básicos para realizar un rebase interactivo sobre una rama local antes de fusionar con main.

```bash
git checkout feature-branch
git rebase -i main
```

## Ejercicio
Realiza un commit en una rama secundaria, luego ejecuta 'git rebase -i' para ordenar tus commits localmente antes de hacer merge.

## Criterios de revisión
El historial debe mostrar una línea recta sin nodos de fusión innecesarios tras el rebase; no deben haberse perdido commits locales.
