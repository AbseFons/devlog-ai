## Objetivo
Aprender a implementar estrategias de versionado en APIs REST para garantizar la compatibilidad hacia atrás y facilitar la evolución del servicio sin romper clientes existentes.

## Explicación
El versionado es crucial para gestionar cambios en la estructura de datos o comportamiento de una API. Existen dos enfoques principales: versionado por URL (ej. /api/v1/usuarios) y versionado por encabezados (ej. Accept: application/vnd.api+json;version=2). El primero es más explícito y fácil de depurar, mientras que el segundo mantiene la ruta limpia pero puede ser menos visible para los desarrolladores. Para una transición suave, se recomienda mantener múltiples versiones simultáneamente durante un periodo de coexistencia, permitiendo a los clientes actualizar su código gradualmente. Es vital documentar claramente las diferencias entre versiones y establecer fechas de retiro (deprecation) con suficiente antelación.

## Ejemplo (no ejecutado automáticamente)
Definición de rutas para dos versiones de una API de gestión de usuarios en un archivo de configuración de servidor web.

```bash
location /api/v1/users {
    proxy_pass http://backend-service;
}

location /api/v2/users {
    proxy_pass http://backend-service-v2;
}
```

## Ejercicio
Crea un archivo de configuración para tu servidor web que defina una ruta para la versión 1.0 y otra para la 2.0 de tu API, asegurando que ambas apunten a diferentes servicios backend.

## Criterios de revisión
El archivo debe contener dos bloques de ubicación distintos con nombres de ruta claros (v1 y v2). Cada bloque debe tener una directiva proxy_pass apuntando a un servicio diferente. No deben existir errores de sintaxis en la configuración del servidor.
