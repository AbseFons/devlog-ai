## Objetivo
Diferenciar conceptualmente merge y rebase en Git, entendiendo cuándo preservar ramas paralelas versus crear una línea de desarrollo única y limpia para facilitar la revisión de cambios.

## Explicación
Git ofrece dos estrategias principales para integrar trabajo: merge y rebase. Merge crea un nuevo commit de fusión que preserva la historia exacta de las ramas, mostrando claramente cuándo se desarrollaron en paralelo. Es ideal para ramas de características activas o cuando el historial debe reflejar fielmente el flujo de trabajo colaborativo. Por otro lado, rebase toma tus commits locales y los aplica uno por uno sobre la rama destino, creando una nueva línea temporal lineal. Esto resulta en un historial más limpio y fácil de leer, pero es peligroso usarlo en ramas compartidas porque altera el historial público. Usa merge para mantener integridad histórica y rebase solo en flujos de trabajo locales o con permisos explícitos.

## Ejemplo (no ejecutado automáticamente)
Comandos para realizar un rebase interactivo, permitiendo editar, borrar o modificar commits antes de fusionarlos a la rama principal.

```bash
git rebase -i origin/main
# Selecciona los commits a mover y edita su orden o contenido
```

## Ejercicio
Realiza un rebase interactivo (-i) sobre la rama 'origin/main' en tu entorno local. Modifica el orden de dos commits recientes para agrupar cambios relacionados, elimina uno que sea una corrección menor ya resuelta y guarda los cambios.

## Criterios de revisión
El historial resultante debe mostrar una línea temporal lineal sin nodos de fusión innecesarios. Los commits modificados deben reflejar la nueva agrupación lógica del trabajo. No deben existir conflictos no resueltos en el estado final.
