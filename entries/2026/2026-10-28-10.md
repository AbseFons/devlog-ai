## Objetivo
Aprender a dividir las tareas de validación, transformación y persistencia de datos en módulos independientes para mejorar el mantenimiento y la seguridad del sistema.

## Explicación
En este nivel de la serie sobre diseño, exploramos cómo aislar la lógica de acceso a datos. En lugar de mezclar consultas SQL con la lógica de negocio, creamos un repositorio dedicado. Este módulo se encarga exclusivamente de interactuar con la base de datos, gestionando conexiones y transacciones. La capa de servicio recibe objetos limpios, sin preocuparse por cómo se almacenan. Esta separación permite cambiar la fuente de datos (por ejemplo, migrar a una nueva base) sin afectar al resto de la aplicación. Además, facilita las pruebas unitarias al poder simular el repositorio con datos falsos.

## Ejemplo (no ejecutado automáticamente)
Un servicio que delega la persistencia de un usuario a un repositorio separado, validando los datos antes de llamar a él.

```javascript
class UserRepository {
  async save(user) {
    const sql = 'INSERT INTO users (name, email) VALUES (?, ?)';
    await db.run(sql, [user.name, user.email]);
  }
}

async function registerUser(userData) {
  if (!userData.email.includes('@')) throw new Error('Email invalido');
  const repo = new UserRepository();
  await repo.save(userData);
}
```

## Ejercicio
Crea una clase 'OrderRepository' que guarde pedidos en una base de datos simulada. Luego, modifica un servicio existente para que use este nuevo repositorio en lugar de ejecutar consultas directamente.

## Criterios de revisión
El código debe tener al menos dos clases separadas (servicio y repositorio). El repositorio no debe contener lógica de validación de negocio. El servicio debe lanzar una excepción si la validación falla antes de llamar al repositorio.
