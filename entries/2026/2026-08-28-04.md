## Objetivo
Al finalizar esta lección, el desarrollador será capaz de explicar por qué la inyección de dependencias facilita las pruebas unitarias y reemplazará instancias concretas con mocks o stubs en su código para desacoplar módulos.

## Explicación
La inyección de dependencias es un patrón de diseño que permite a una clase recibir sus dependencias desde el exterior, en lugar de crearlas internamente. Esto rompe acoplamientos fuertes y hace que el código sea más modular y mantenible. Imagina una clase 'Reporte' que necesita un servicio de 'Email'. En lugar de que 'Reporte' instancie directamente la clase 'EmailService', se le pasa una instancia a través del constructor. De esta forma, si quieres cambiar el comportamiento (por ejemplo, enviar correos falsos para pruebas), solo modificas dónde se crea la dependencia, no dentro de la lógica del negocio.

## Ejemplo (no ejecutado automáticamente)
```python
class EmailService:
    def enviar(self, destinatario: str, cuerpo: str) -> bool:
        print(f"Enviando a {destinatario}: {cuerpo}")
        return True

class ReporteGenerador:
    def __init__(self, servicio_email: EmailService):
        self.servicio = servicio_email
    
    def generar(self, destinatario: str) -> bool:
        return self.servicio.enviar(destinatario, "Reporte mensual")

# Uso realista con inyección
servicio_real = EmailService()
generador = ReporteGenerador(servicio_real)
resultado = generador.generar("juan@empresa.com")
```

Luego, instancia una clase 'PasarelaFalsa' que simule pagos exitosos y otra 'PasarelaReal' que use una API externa (sin credenciales). Inyecta ambas en 'Pagos' y verifica que el comportamiento cambie según la inyección.

## Criterios de revisión
El código debe tener dos clases distintas para las pasarelas. El constructor de 'Pagos' no debe crear instancias internas. Debe existir una función de prueba que inyecte la clase falsa y otra que inyecte la real, demostrando el cambio de comportamiento sin modificar la lógica interna de 'Pagos'.
