## Objetivo
Aprender a distinguir entre la lógica de validación de datos y su transformación en una arquitectura limpia, evitando acoplar reglas de negocio con operaciones de persistencia.

## Explicación
En el diseño de software moderno, la separación de responsabilidades exige que la validación de entrada sea independiente de la transformación de datos. Un patrón común es encapsular las reglas de negocio en un servicio de validación puro que devuelve errores específicos, mientras que la capa de persistencia se encarga exclusivamente de mapear objetos válidos a entidades de base de datos. Esto permite reutilizar la lógica de validación para diferentes destinos (APIs, archivos, otras bases de datos) sin duplicar código. Además, facilita las pruebas unitarias al poder verificar las reglas de negocio aisladamente del contexto de infraestructura. Al mantener estas capas separadas, el sistema gana flexibilidad y mantenibilidad, cumpliendo con los principios SOLID.

## Ejemplo (no ejecutado automáticamente)
Un servicio que valida un usuario antes de transformarlo en una entidad de base de datos, devolviendo errores si no cumple las reglas.

```javascript
const validarUsuario = (datos) => {
  if (!datos.email || !datos.password) throw new Error('Faltan campos');
};

const transformarEntidad = (valido) => ({ id: 1, ...valido });
```

## Ejercicio
Crea una función 'procesarPago' que primero valide los datos de la tarjeta y luego transforme el objeto en un registro de transacción. Asegúrate de lanzar una excepción si la validación falla antes de intentar la transformación.

## Criterios de revisión
El código debe tener dos funciones separadas: una para validar y otra para transformar. La función principal debe llamar a la de validación primero y solo ejecutar la transformación si no hay errores.
